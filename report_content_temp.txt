                                       ABSTRAK

   Pemeliharaan dan pengembangan perangkat lunak mobile kerap terhambat ketika Activity
utama menanggung terlalu banyak tanggung jawab, sebuah pola yang dikenal sebagai God Class.
Dokumen ini menyajikan tahapan perbaikan kode (reengineering) pada aplikasi Weather App
yang dibangun untuk platform Android. Analisis awal kode sumber mengungkap HomeActivity
sebagai titik sentral di mana logika UI, network, dan layanan lokasi dikonsolidasikan, melanggar
prinsip pemisahan tanggung jawab. Selain itu, ditemukan data yang disematkan (hardcoded)
yang   berpotensi     menimbulkan    masalah    fleksibilitas.   Proses   kerja   ini   mengadopsi
langkah-langkah penemuan code smell, diikuti dengan implementasi teknik-teknik perombakan
struktur kode (refactoring). Teknik yang krusial adalah Ekstraksi Kelas dan Ekstraksi Metode,
serta pembersihan kode usang (Dead Code removal). Dampak positif dari refactoring ini adalah
organisasi kode yang sangat modular dan peningkatan signifikan dalam keterbacaan. Struktur
baru kini berjalan sesuai dengan Single Responsibility Principle (SRP), dengan fungsionalitas
aplikasi yang tidak terpengaruh.


                                    1.​ PENDAHULUAN

1.1​Latar Belakang

Dalam pengembangan aplikasi Android, seringkali pengembang menempatkan seluruh logika
bisnis dan manajemen data di dalam Activity. Seiring bertambahnya fitur, kelas ini menjadi
sangat besar dan sulit dipelihara. Hal ini memunculkan "Code Smells", indikator kelemahan
desain yang dapat menyebabkan technical debt.


Kelompok kami memilih studi kasus aplikasi Weather App yang memiliki indikasi kuat God
Class dan Hardcoded Values. Kode asli menunjukkan struktur yang mencampurkan logika
networking (Volley) dan manipulasi UI dalam satu file, sehingga sangat relevan untuk dilakukan
proses refactoring.
1.2​Identifikasi Code Smells

Berdasarkan analisis awal menggunakan referensi materi kuliah, ditemukan beberapa code
smells dominan:

1.​ The Bloater - God Class / Large Class:
    Kelas HomeActivity.java memiliki tanggung jawab yang terlalu besar (UI, Permission, GPS
    Location, API Calls).
2.​ The Bloater - Long Method:
    Method onCreate dan getTodayWeatherInfo terlalu panjang dan melakukan banyak tugas yang
    tidak saling berkaitan secara langsung.
3.​ Hardcoded Values:
    Kelas Toaster.java menggunakan string warna hex ("#454B54") secara langsung di dalam
    kode, bukan menggunakan resources Android (colors.xml), menyulitkan perubahan tema.
4.​ The Dispensable - Dead Code / Lazy Class:
    Kelas CityFinder.java hanya berisi metode statis yang jarang digunakan dan kurang kohesif
    sebagai kelas yang berdiri sendiri.
5.​ Improper Instantiation:
    Kelas URL.java diinstansiasi (new URL()) hanya untuk memanggil metode yang seharusnya
    bersifat statis.




1.3​Alasan Code Smell

Code smells tersebut muncul karena:

1. Pelanggaran Single Responsibility Principle (SRP):
Pengembang awal menggabungkan logika pengambilan data (Model) dan tampilan (View) dalam
satu Activity, padahal HomeActivity seharusnya hanya bertanggung jawab menampilkan data.

2. Kesulitan Pengujian (Testing):
Logika bisnis yang bercampur dengan logika UI membuat unit testing sulit dilakukan.

3. Redundansi:
Penggunaan nilai hardcoded menyulitkan pemeliharaan jangka panjang.
                                     2.​ METODOLOGI

Proses reengineering/refactoring dilakukan dengan langkah-langkah berikut:

2.1​Persiapan Lingkungan

Kami menggunakan Git sebagai Version Control System untuk melacak perubahan sebelum dan
sesudah refactoring. Pengembangan dilakukan menggunakan IDE Android Studio. Setiap
langkah refactoring dilakukan secara bertahap untuk memastikan aplikasi tetap berjalan di setiap
tahapnya.

2.2​Teknik Refactoring yang Digunakan

2.2.1​Extract Class (Modularisasi)

Teknik ini digunakan untuk memecah God Class HomeActivity. Kami memisahkan tanggung
jawab ke dalam kelas-kelas baru:

   ●​ WeatherRepository.java:            Menangani       seluruh     logika     jaringan      (API
       Calls).

   ●​ LocationManager.java:           Menangani   izin           lokasi  dan   pengambilan
       koordinat    GPS          (memindahkan   logika           dari   HomeActivity   dan
       CityFinder).

   ●​ HomeActivity.java: Sekarang hanya fokus pada inisialisasi UI dan
       menampilkan data.


2.2.2​Extract Method
     Teknik ini diterapkan pada method onCreate di HomeActivity.

     Logika inisialisasi dipecah menjadi metode privat yang deskriptif:
        ●​ initHelpers()
        ●​ setupUI()
        ●​ setupListeners().
2.2.3​Remove Dead Code & Replace Constants


    ●​ Menghapus    kelas CityFinder.java karena fungsinya digabungkan ke
         LocationManager yang lebih kohesif.

    ●​ Mengubah    metode di URL.java              menjadi   static     agar   dapat     diakses
         tanpa instansiasi objek.

    ●​ Mengganti string warna hardcoded di Toaster.java dengan referensi
         R.color.

3.3​Validasi Fungsional

Setelah dilakukan perubahan struktur, pengujian manual (Black Box Testing) dilakukan. Fitur
utama seperti deteksi lokasi otomatis, pengambilan data cuaca hari ini, dan tampilan UI
dipastikan tetap berjalan normal tanpa crash, membuktikan bahwa perilaku eksternal program
tidak berubah.
                          4.​ PEMBAHASAN (DISCUSSION)

4.1​Tantangan (Challenges)

Tantangan terbesar adalah memisahkan logika Asynchronous (seperti request jaringan Volley
dan callback lokasi) dari Activity. Activity kehilangan konteks untuk memperbarui UI saat data
selesai dimuat karena proses jaringan berjalan di latar belakang.

4.2​Solusi

Solusi yang diterapkan adalah menggunakan pola Callback Interface (OnWeatherDataListener,
OnLocationListener) di dalam Repository dan Manager. HomeActivity mengimplementasikan
interface ini, sehingga tetap dapat menerima hasil data secara asinkron tanpa harus mengetahui
detail implementasi pengambilan datanya.

                                     5.​ KESIMPULAN

Berdasarkan proses code reengineering yang telah dilakukan, dapat disimpulkan bahwa:

   1.​ Migrasi aplikasi dari struktur terpusat (God Class) menuju tata letak yang lebih
       modular telah diselesaikan dengan sukses.

   2.​ Penerapan teknik Extract Class dan Extract Method berhasil memisahkan
       concern antara UI, Data, dan Lokasi sesuai prinsip Separation of Concerns.


   3.​ Kode menjadi lebih mudah dibaca (readable) dan lebih siap untuk pengembangan
       fitur masa depan karena isolasi logika yang baik.
